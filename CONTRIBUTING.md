# Как мы работаем с кодом

Короткая версия: **в `main` напрямую не пишем. Любое изменение — ветка → pull request → код-ревью → зелёный CI → squash-merge.** Остальное ниже.

## 1. Задача

- Работа начинается с issue. Нет issue — сначала заводим, с пунктами ТЗ (`docs/TZ.md`) и критериями готовности, как в существующих.
- Одна задача — один PR. Если задача разрослась, делим её на несколько issues, а не делаем PR на 3000 строк.
- Перед началом читаем issue и указанные пункты ТЗ целиком. Если ТЗ не отвечает на вопрос — спрашиваем в issue, не додумываем.

## 2. Ветка

- От актуального `main`: `git switch main && git pull --ff-only && git switch -c feat/<номер>-<кратко>`.
- Префиксы: `feat/` новая функциональность, `fix/` исправление, `chore/` инфраструктура и зависимости, `docs/` документация. Пример: `feat/8-postgres-migrations`, `fix/42-timer-midnight`.
- Ветка живёт не дольше нескольких дней. Если `main` ушёл вперёд — `git rebase main`, не merge.

## 3. Коммиты

- На русском, в повелительном наклонении, первая строка до 72 символов: «Добавить миграцию users и project_members». Тело — зачем, а не что (что видно в диффе).
- Без строк Co-Authored-By и упоминаний инструментов, которыми писался код.
- Коммитим рабочее состояние: код компилируется, тесты проходят. «WIP» не пушим в PR.
- Форматирование и линт до коммита: `make fmt lint test`, `cd web && npm run lint && npm run build`.

## 4. Pull request

- PR открывается в `main` сразу как есть что показать; пока не готов — черновик (draft).
- Заголовок = будущее сообщение squash-коммита: «Миграции PostgreSQL и подключение GORM (#8)».
- Описание по шаблону `.github/pull_request_template.md`: `Closes #<номер>`, что сделано, как проверить, чек-лист критериев готовности из issue.
- PR должен быть маленьким: до ~400 строк изменений без учёта сгенерированного кода и тестов. Большой PR ревьюится хуже и дольше.
- Менялся API — в PR есть обновлённый Swagger (`make swag`). Менялась схема — есть `up` и `down` миграции, и `down` проверен.
- Секретов, `.env`, `node_modules`, собранной статики в диффе нет.

## 5. Код-ревью

- **Мерж только после ревью, и одного ревью достаточно.** Ревью делает Claude Code командой `/code-review <номер PR>` (или по ветке); результат фиксируется комментарием в PR — найденные проблемы и вердикт. Второго ревью не требуется: как только замечания первого закрыты, PR можно сливать.
- Ревью проверяет: соответствие ТЗ (пункты из issue), права по §2, формат ошибок §9.3, транзакции и outbox там, где меняются данные, тесты на новые правила, отсутствие лишних зависимостей.
- Замечания исправляются новыми коммитами в ту же ветку, без force-push: ревьюеру нужно видеть, что изменилось с прошлого раза.
- Споры решает ТЗ. Если ТЗ не покрывает вопрос, его сначала дописывают в ТЗ (исходник в Claude Docs), потом правят код.

## 6. Слияние

- Условия: одно ревью пройдено, все его замечания закрыты, CI зелёный (`API (Go)`, `Web (React)`, `Docker image`, `Скрипты (shellcheck)`), ветка актуальна относительно `main`. Больше ничего не требуется — ждать второго ревьюера или «ещё раз посмотреть завтра» не нужно.
- Стратегия — **squash**: один коммит на задачу, сообщение = заголовок PR + `Closes #N`. Rebase и merge-коммиты в репозитории отключены.
- После слияния ветка удаляется (включено автоматически). Issue закрывается через `Closes #N`, эпик обновляется сам через sub-issues.
- `main` защищён: прямой push, force-push и удаление запрещены, PR обязателен, CI обязателен, все обсуждения в PR должны быть закрыты. Обязательный approve в GitHub не включён: свой PR одобрить нельзя, а разработчик пока один. Появится второй аккаунт — включаем «1 approve» и правило становится принудительным.

## 7. Тесты — что обязательно

- Новое правило ТЗ → тест на него. Переходы §4, парсер длительности §6.1, права §2 — табличные тесты.
- Всё, что трогает базу, тестируется на настоящем PostgreSQL через testcontainers; моки базы не принимаются.
- Гонки (взятие задачи, запуск спринта, номер задачи) проверяются реальной конкурентностью.
- Покрытие серверного кода не падает ниже 80% — CI это проверяет.

## 8. Релиз на стенд

- Релиз = git-тег `vX.Y.Z` на `main` (semver: major — несовместимый API, minor — функциональность, patch — исправления).
- Тег собирает образ в GHCR; на сервере `deploy.sh vX.Y.Z` делает pull, миграции и перезапуск с откатом при неудаче `/health` (issue #6).
- Миграции только вперёд-совместимые: сначала добавляем колонку, выкатываем код, потом удаляем старое следующим релизом. Иначе откат образа сломается об схему.
- Что вошло в релиз — в описании тега (GitHub Release), списком закрытых issues.

## 9. Чего не делаем

- Не пушим в `main`, не делаем force-push в чужие и общие ветки.
- Не отключаем и не помечаем `skip` тесты, чтобы «позеленить» CI.
- Не добавляем зависимость без обоснования в PR.
- Не меняем `docs/TZ.md` напрямую — только через исходник в Claude Docs и перевыгрузку.
- Не трогаем чужие сервисы на сервере (mahalla, quizlet) и их nginx.
