# ТЗ: Система управления задачами и временем с Telegram-ботом

Версия от 12.10.2026. Исходник — Claude Docs: https://claude.ai/code/artifact/a6dc5e67-f00c-41be-a9d7-4d91a8780950

## 1. Общие сведения

Система — веб-приложение для ведения задач по модели Jira: задачи с фиксированным набором статусов, учёт времени по каждой задаче, работа спринтами. Дополнительно Telegram-бот, через который участники берут задачи в работу прямо в групповом чате, а бот публикует в группу, кто какую задачу взял.

**Что входит в объём работ**

- Веб-интерфейс: доска, список задач, карточка задачи, спринты, отчёты по времени.
- Серверная часть с REST API.
- Telegram-бот (личный чат и групповой чат).
- Авторизация и роли.

**Что не входит в объём работ**

- Мобильные приложения (iOS, Android).
- Интеграция с Jira, GitLab, календарями (связь с GitHub — раздел 12).
- Биллинг, тарифы, мультитенантность (система разворачивается для одной компании).
- Wiki, документы, базы знаний.
- Настройка статусов под проект, story points, подзадачи и связи между задачами.
- Вход через Telegram без пароля; уведомления по email о событиях (почта только для ссылок на установку пароля).

**Термины**

| Термин | Значение |
| --- | --- |
| Проект | Контейнер задач с собственным ключом (например `TM`). Все задачи принадлежат ровно одному проекту. |
| Задача | Единица работы с ключом вида `TM-123`, статусом, исполнителем, оценкой и списанным временем. |
| Спринт | Ограниченный по датам период работы, в который входит набор задач проекта. |
| Бэклог | Задачи проекта, не включённые ни в один спринт. |
| Статус | Текущее состояние задачи из фиксированного списка (раздел 4). |
| Исполнитель | Пользователь, который взял задачу в работу или назначен менеджером. У задачи не более одного исполнителя. |
| Оценка | Плановое время на задачу в часах и минутах. |
| Списание времени | Запись о фактически потраченном времени по задаче. |
| Привязка | Связь аккаунта пользователя системы с его Telegram-аккаунтом. |
| Менеджер проекта | Участник проекта с ролью manager: управляет задачами, спринтами, участниками и настройками одного проекта (раздел 2). |
| Администратор системы | Глобальная роль: создаёт проекты и пользователей, имеет все права менеджера во всех проектах. |
| Группа проекта | Telegram-группа, подключённая к проекту (8.2); одна группа может обслуживать несколько проектов. |

## 2. Роли и права доступа

В системе три роли. Роль назначается на уровне проекта: один пользователь может быть менеджером в одном проекте и исполнителем в другом. Роль «Администратор системы» глобальная и одна на всю установку.

| Действие | Администратор системы | Менеджер проекта | Исполнитель |
| --- | --- | --- | --- |
| Создавать проекты, удалять проекты | Да | Нет | Нет |
| Приглашать пользователей в проект, менять их роли | Да | Да | Нет |
| Создавать задачи | Да | Да | Да |
| Редактировать любую задачу проекта (все поля) | Да | Да | Нет |
| Редактировать задачу, где он автор или исполнитель | Да | Да | Да |
| Удалять задачи | Да | Да | Нет |
| Назначать исполнителя на любую задачу | Да | Да | Нет |
| Брать задачу себе (назначить себя исполнителем) | Да | Да | Да |
| Менять статус задачи (по правилам раздела 4) | Да | Да | По разделу 4: своих задач, а также принять или вернуть задачу, где он автор |
| Создавать, запускать, завершать спринты | Да | Да | Нет |
| Добавлять и убирать задачи из спринта | Да | Да | Нет |
| Списывать время на задачу | Да | Да | Только на свои задачи |
| Редактировать и удалять чужие записи времени | Да | Да | Нет |
| Смотреть отчёты по времени всего проекта | Да | Да | Только по себе |
| Подключать Telegram-группу к проекту | Да | Да | Нет |
| Настраивать уведомления бота для проекта | Да | Да | Нет |
| Добавлять вложения и комментарии, создавать задачи командой /new | Да | Да | Да |
| Удалять чужие вложения и комментарии | Да | Да | Нет (только свои) |
| Менять порядок задач внутри секции бэклога или спринта | Да | Да | Да |
| Восстанавливать удалённые задачи, смотреть корзину и журнал аудита | Да | Нет | Нет |
| Архивировать, удалять и восстанавливать проект | Да | Нет | Нет |
| Заводить и деактивировать пользователей | Да | Нет | Нет |

«Свои задачи» означает задачи, где пользователь указан исполнителем. Пользователь без роли в проекте не видит проект и его задачи ни в веб-интерфейсе, ни через бота.

## 3. Сущности и поля

Основные сущности: Пользователь, Проект, Задача, Спринт, Запись времени. Вспомогательные: Участник проекта, Комментарий, История изменений, Вложение (3.9) и служебные сущности из 3.8. Все даты и время хранятся в UTC, отображаются в часовом поясе пользователя. Все сущности имеют поля `id` (UUID v4), `created_at`, `updated_at`.

**3.1. Пользователь (User)**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `email` | строка | Да | Уникальный, логин для входа |
| `password_hash` | строка | Да | bcrypt, cost 12 |
| `display_name` | строка | Да | 1–80 символов |
| `timezone` | строка | Да | IANA, по умолчанию `Europe/Moscow` |
| `telegram_user_id` | целое | Нет | Уникальный, заполняется при привязке бота |
| `telegram_username` | строка | Нет | Без `@`, обновляется при каждом сообщении боту |
| `is_system_admin` | булево | Да | По умолчанию `false` |
| `is_active` | булево | Да | Деактивированный не может войти и не получает уведомления. При деактивации: таймер останавливается с записью; открытые задачи освобождаются — исполнитель очищается, задачи в in\_progress возвращаются в todo, в историю пишется «снят при деактивации»; менеджеры его проектов получают уведомление со списком освобождённых задач; привязка Telegram снимается. Закрытые задачи, записи времени и история остаются. Если пользователь — единственный менеджер проекта, деактивация отклоняется (409 LAST\_MANAGER) до назначения другого менеджера |
| `notification_settings` | JSON | Да | Включённые личные уведомления из 8.7; по умолчанию все включены |

**3.2. Проект (Project)**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `key` | строка | Да | 2–10 латинских заглавных букв, уникальный, не меняется после создания |
| `name` | строка | Да | 1–100 символов |
| `description` | текст | Нет | До 2000 символов |
| `task_counter` | целое | Да | Счётчик номеров задач, только растёт, номера не переиспользуются; номер выдаётся атомарно (UPDATE … RETURNING), одновременное создание из веба и Telegram не даёт одинаковых номеров |
| `telegram_chat_id` | целое | Нет | Привязанная группа, не более одной на проект; одна группа может быть привязана к нескольким проектам |
| `is_archived` | булево | Да | В архивном проекте запрещены любые изменения: доска и карточки открываются только для чтения, API и бот отвечают 409 PROJECT\_ARCHIVED, запущенные таймеры останавливаются при архивации. Архивные проекты скрыты в списке проектов за фильтром «Архив», отчёты по ним доступны |
| `timezone` | строка | Да | IANA, по умолчанию Europe/Moscow; по нему отправляется ежедневная сводка (8.6) |
| `notification_settings` | JSON | Да | Включённые события бота в группе из 8.6; по умолчанию как в таблице 8.6 |
| `daily_summary_time` | время | Да | Время ежедневной сводки по часовому поясу проекта, по умолчанию 10:00 |
| `deleted_at` | дата-время | Нет | Мягкое удаление (только администратор): проект исчезает из списков, бота и отчётов, Telegram-группа отключается; задачи, записи времени и вложения сохраняются. Восстанавливает администратор (POST /projects/{key}/restore); ключ удалённого проекта нельзя занять новым |

Связь «Участник проекта» (ProjectMember): `project_id`, `user_id`, `role` (одно из `manager`, `member`). Пара `project_id` + `user_id` уникальна.

**3.3. Задача (Task)**

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| `project_id` | UUID | Да | Не меняется после создания |
| `number` | целое | Да | Берётся из `task_counter` проекта |
| `key` | строка | Да | Вычисляемое: `{project.key}-{number}`, например `TM-42` |
| `title` | строка | Да | 1–200 символов |
| `description` | текст | Нет | Markdown, до 20 000 символов |
| `type` | перечисление | Да | `task`, `bug`, `feature`. По умолчанию `task` |
| `status` | перечисление | Да | См. раздел 4. При создании всегда `todo` |
| `priority` | перечисление | Да | `low`, `medium`, `high`, `critical`. По умолчанию `medium` |
| `reporter_id` | UUID | Да | Автор, ставится автоматически, не меняется |
| `assignee_id` | UUID | Нет | Исполнитель. Пусто = задача свободна |
| `sprint_id` | UUID | Нет | Пусто = задача в бэклоге |
| `estimate_minutes` | целое | Нет | Оценка в минутах, от 1 до 60 000 |
| `spent_minutes` | целое | Да | Вычисляемое: сумма всех записей времени по задаче |
| `due_date` | дата | Нет | Срок выполнения (дата без времени). Задача просрочена, если дата раньше сегодняшней по часовому поясу проекта и задача не закрыта |
| `labels` | массив строк | Нет | До 10 меток, каждая до 30 символов; хранится как jsonb |
| `started_at` | дата-время | Нет | Момент первого перехода в `in_progress` |
| `completed_at` | дата-время | Нет | Момент перехода в `done`, сбрасывается при переоткрытии |
| `position` | число | Да | Ручной порядок задачи внутри своей секции: спринт или бэклог (7.4) |
| `telegram_message_id` | целое | Нет | id сообщения задачи в группе проекта (8.3); обновляется, если бот публикует сообщение заново |
| `version` | целое | Да | Растёт на 1 при каждом изменении. PATCH передаёт текущее значение в If-Match; если задачу уже изменил другой — 409 VERSION\_CONFLICT, интерфейс показывает чужие правки и предлагает повторить |
| `deleted_at` | дата-время | Нет | Мягкое удаление (раздел 4); заполнено = задача удалена |

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |

| `user_id` | UUID | Да | Кто списал время |

**3.6. Комментарий (Comment)**: `task_id`, `author_id`, `body` (Markdown, 1–5000 символов), `source` (`web`, `telegram`). Редактировать и удалять комментарий может автор и менеджер проекта.

**3.7. История изменений (TaskHistory)**: `task_id`, `user_id`, `field` (имя изменённого поля), `old_value`, `new_value`, `source` (`web`, `telegram`, `api`). Запись создаётся на каждое изменение полей `status`, `assignee_id`, `sprint_id`, `priority`, `estimate_minutes`, `due_date`, `title`, а также type; удаление и восстановление задачи записываются как изменение поля deleted\_at. История не редактируется и не удаляется.

| SprintLog | `sprint_id`, `task_id`, `user_id`, `action` (`added`, `removed`) | Задачи, добавленные и убранные после старта (5.3) |
| Notification | `user_id`, `task_id`, `type`, `payload`, `read_at` | Уведомления в веб-интерфейсе (7.7), хранятся 30 дней |
| ProcessedUpdate | `update_id`, `processed_at` | Обработанные обновления Telegram (8.8), хранятся 24 часа |

| AuditLog | actor\_id, project\_id, action, entity\_type, entity\_id, old\_value, new\_value, source | Действия менеджеров и администраторов: участники и роли, настройки проекта, подключение групп, правка и удаление чужих записей времени, удаление и восстановление задач, создание и деактивация пользователей. | SprintDailySnapshot | sprint\_id, date, open\_tasks, open\_estimate\_minutes, done\_tasks | Снимок активного спринта на конец каждого дня по поясу проекта (делает воркер в 00:00) и в момент закрытия; берндаун 5.6 строится по снимкам |

**3.9. Вложение (Attachment):** `task_id`, `author_id`, `file_name`, `mime_type`, `size_bytes`, `storage_path`. Размер файла до 50 МБ, тип любой. Добавляет любой участник проекта, удаляет автор файла и менеджер. Файлы хранятся на диске сервера (Docker volume) и входят в ежедневный бэкап. Вложения добавляются только в веб-интерфейсе. Скачивание — по временной подписанной ссылке (10 минут), которую API выдаёт после проверки прав; файл отдаётся с заголовками Content-Disposition: attachment и X-Content-Type-Options: nosniff и никогда не открывается в браузере как страница (защита от XSS через HTML-файлы).

## 4. Статусы задачи и переходы

Набор статусов фиксированный, одинаковый для всех проектов и не настраивается. Переходы разрешены только по схеме ниже; любой другой переход сервер отклоняет с ошибкой `409 INVALID_TRANSITION`.

```
                 отказаться                        вернуть на доработку
            ┌──────────────────┐              ┌─────────────────────────┐
            ▼                  │              ▼                         │
  todo ──взять в работу──▶ in_progress ──на проверку──▶ review ──принять──▶ done
    ▲                          ▲                          │                 │
    │                          └──────── переоткрыть ─────┼─────────────────┘
    │                                                     │
    └──── вернуть в бэклог ──── cancelled ◀── отменить ───┘
                                   ▲          (из todo, in_progress, review)
                                   └──────────────────────┘
```

Основной путь слева направо. Петли сверху возвращают задачу назад, нижняя ветка — отмена из трёх незакрытых статусов и возврат отменённой задачи в бэклог.

| Переход | Кто может | Что происходит дополнительно |
| --- | --- | --- |
| `todo` → `in_progress` (взять в работу) | Исполнитель задачи; любой участник, если исполнитель пуст; менеджер | Если исполнитель пуст, исполнителем становится тот, кто перевёл. Если исполнитель задан и это другой пользователь, переход разрешён только исполнителю и менеджеру. При первом переходе заполняется `started_at` |
| `in_progress` → `todo` (отказаться) | Исполнитель; менеджер | Поле `assignee_id` очищается |
| `in_progress` → `review` (на проверку) | Исполнитель; менеджер | Нет |
| `review` → `in_progress` (вернуть на доработку) | Автор задачи; менеджер | Обязателен комментарий с причиной, минимум 5 символов |
| `review` → `done` (принять) | Автор задачи, если он не исполнитель; менеджер | Заполняется `completed_at` |
| `done` → `in_progress` (переоткрыть) | Менеджер | `completed_at` очищается; исполнитель сохраняется, а если он деактивирован — менеджер обязан выбрать активного исполнителя при переоткрытии. Если задача в закрытом спринте, она переносится в активный спринт (в журнал спринта как «добавлено после старта»), а если активного спринта нет — в бэклог |
| `todo`, `in_progress`, `review` → `cancelled` (отменить) | Менеджер | Обязателен комментарий с причиной. Исполнитель сохраняется |
| `cancelled` → `todo` (вернуть в бэклог) | Менеджер | Поле `assignee_id` очищается, `sprint_id` очищается |

**Дополнительные правила**

- Назначить исполнителя можно в любом статусе, кроме `done` и `cancelled`.
- Снять исполнителя с задачи в статусе `in_progress` нельзя: сначала переход в `todo`.
- Списывать время на задачу, которая не в закрытом спринте (6.5), можно в любом статусе, кроме `cancelled`.
- Каждый переход записывается в историю задачи с указанием, кто и откуда (веб, Telegram, API) его сделал.
- Статусы `done` и `cancelled` считаются закрытыми; закрытые задачи не показываются на доске по умолчанию и не переносятся в следующий спринт.
- Если автор задачи — её исполнитель, принять задачу (`review` → `done`) может только менеджер. Вернуть свою задачу на доработку (`review` → `in_progress`) он может сам.
- Удаление задачи мягкое: заполняется `deleted_at`, задача исчезает с доски, из бэклога, поиска и бота, запущенный на ней таймер останавливается. Записи времени остаются в отчётах с пометкой «удалённая задача». Сообщение задачи в группе редактируется на «Задача удалена». Восстановить может администратор системы.

## 5. Спринты

В проекте одновременно не более одного активного спринта. Запланированных спринтов может быть сколько угодно. Задача принадлежит не более чем одному спринту. Запуск, завершение и удаление спринта выполняются в транзакции с блокировкой строки проекта: два одновременных запуска не дадут двух активных спринтов.

**5.1. Создание.** Менеджер создаёт спринт с названием, целью и датами (даты необязательны до запуска). Спринт получает состояние `planned`. Задачи добавляются в спринт из бэклога перетаскиванием или через поле «Спринт» в карточке задачи.

**5.2. Запуск.** Менеджер нажимает «Запустить спринт». Условия, которые сервер проверяет и при нарушении отказывает с ошибкой `409`:

1. В проекте нет другого спринта в состоянии `active`.
2. Заполнены `start_date` и `end_date`, `end_date` позже `start_date`, длительность не более 42 дней.
3. В спринте есть хотя бы одна задача.

При запуске спринт переходит в `active`, система фиксирует «объём на старте»: список задач и сумму их оценок в минутах. Задачи без оценки входят в список с оценкой 0; их число показывается при запуске и в отчёте как «без оценки: N». Эти данные нужны для отчёта по спринту и не меняются.

**5.3. Во время активного спринта.** Задачи можно добавлять и убирать; каждое такое изменение попадает в историю задачи и в журнал спринта как «добавлено после старта» или «убрано после старта». Даты активного спринта может менять только менеджер; при наступлении `end_date` спринт не закрывается автоматически, а помечается в интерфейсе как «просрочен».

**5.4. Завершение.** Менеджер нажимает «Завершить спринт». Система показывает сводку: сколько задач в `done`, сколько незакрытых, и спрашивает, куда перенести незакрытые задачи: в бэклог или в один из запланированных спринтов (один выбор для всех задач сразу). Незакрытыми считаются задачи в `todo`, `in_progress`, `review`. Задачи в `done` и `cancelled` остаются в завершённом спринте. Спринт переходит в `closed`, заполняется `closed_at`. Закрытый спринт нельзя переоткрыть, в него нельзя добавлять задачи.

**5.5. Удаление.** Удалить можно только спринт в состоянии `planned`; его задачи возвращаются в бэклог.

**5.6. Отчёт по спринту.** Доступен для `active` и `closed` спринтов и содержит:

- число задач и сумму оценок на старте;
- число задач и сумму оценок на текущий момент (или на момент закрытия);
- задачи, добавленные и убранные после старта;
- сумму списанного времени по задачам спринта с разбивкой по исполнителям;
- берндаун: по дням спринта сумма оценок незакрытых задач (в часах) против идеальной прямой от объёма на старте до нуля; точки берутся из ежедневных снимков спринта (3.8).

## 6. Учёт времени

Время учитывается в минутах и привязано к конкретной задаче и конкретному пользователю. Списать время без задачи нельзя.

**6.1. Формат ввода и отображения.** Пользователь вводит время строкой вида `2h 30m`, `45m`, `3h`, `1d` (где `1d` = 8 часов). Допустимые единицы: `d`, `h`, `m`; порядок строго от большей к меньшей, пробелы между частями необязательны. Строка, не подходящая под формат, отклоняется с ошибкой `400 INVALID_DURATION`. Отображение везде в том же формате: `2h 30m`; в отчётах и таблицах дополнительно в десятичных часах с двумя знаками (`2.50`).

**6.2. Оценка.** Поле `estimate_minutes` задаётся при создании или позже. Изменение оценки в статусе `in_progress` и позже доступно только менеджеру и фиксируется в истории. В карточке задачи показываются три числа: оценка, списано, остаток (оценка минус списано, не меньше нуля) и прогресс-бар. Если списано больше оценки, прогресс-бар подсвечивается красным и показывается перерасход.

**6.3. Ручное списание.** В карточке задачи кнопка «Списать время» открывает форму: длительность (обязательно), дата работы (по умолчанию сегодня, не позже сегодня, не раньше даты создания задачи), комментарий (необязательно). Сумма записей одного пользователя за одну дату по всем задачам не может превышать 24 часа; при превышении ошибка `409 DAILY_LIMIT_EXCEEDED`.

**6.4. Таймер.** В карточке задачи и на доске кнопка «Старт». Правила:

- У пользователя не более одного запущенного таймера. Запуск таймера на другой задаче автоматически останавливает текущий и создаёт запись времени.
- Таймер можно запустить только на задаче в статусе `in_progress`, где пользователь исполнитель.
- При остановке создаётся запись времени с `source = timer`, длительность округляется вверх до минуты. Если таймер работал меньше 1 минуты, запись не создаётся. Если таймер работал через полночь по часовому поясу пользователя, создаются две записи: часть до полуночи — на предыдущую дату, часть после — на новую; каждая часть округляется вверх до минуты. Если запись таймера превысит дневной лимит 24 часа (6.3), она обрезается до остатка лимита за эту дату, и пользователь получает уведомление; если остатка нет, запись не создаётся.
- Таймер, который работает больше 12 часов, останавливается сервером автоматически на отметке 12 часов, пользователь получает уведомление в Telegram (если привязан) и в веб-интерфейсе.
- Перевод задачи из `in_progress` в любой другой статус останавливает запущенный на ней таймер.
- Запущенный таймер виден в шапке веб-интерфейса на всех страницах: ключ задачи и прошедшее время, кнопка «Стоп».

**6.5. Редактирование и удаление записей.** Автор записи может редактировать и удалять свои записи в течение 7 календарных дней после `work_date`. Менеджер проекта — любые записи без ограничения по сроку. По задачам закрытого спринта записи времени никто не добавляет, не редактирует и не удаляет.

**6.6. Отчёты.** Страница «Отчёты» с фильтрами: период (дата с — дата по, по умолчанию текущая неделя), проект, спринт, пользователь. Два представления:

1. По пользователям: строка на пользователя, столбец на день периода, в ячейке сумма минут, итог по строке и по столбцу.
2. По задачам: строка на задачу (ключ, название, исполнитель, статус, оценка, списано за период, списано всего).

Оба представления выгружаются в CSV в формате для русского Excel: кодировка UTF-8 с BOM, разделитель «;», время в десятичных часах с десятичной запятой (2,50), даты dd.mm.yyyy. В представлении по пользователям столбцы — все дни периода, суббота и воскресенье выделены серым. Исполнитель видит отчёты только по себе, фильтр «пользователь» для него заблокирован.

## 7. Веб-интерфейс

Восемь экранов: вход, список проектов, доска, бэклог и спринты, карточка задачи, отчёты, профиль, настройки проекта. Интерфейс на русском языке, адаптивный до ширины 1024 px; на меньших экранах корректная работа не требуется. Даты в интерфейсе — dd.mm.yyyy, время — по часовому поясу пользователя.

**7.1. Вход.** Форма email + пароль. Саморегистрации нет: пользователей создаёт администратор системы, пользователь получает ссылку для установки пароля на email (ссылка действует 24 часа). Восстановление пароля через email таким же способом. Пароль не короче 10 символов. Ссылка одноразовая и гасится после использования. Первый администратор системы создаётся командой на сервере: docker compose exec api tasks admin create --email \<email>; команда отправляет письмо со ссылкой, а если SMTP не настроен — печатает ссылку в консоль.

**7.2. Список проектов.** Карточки проектов, в которых пользователь участник: ключ, название, активный спринт и его даты, число открытых задач, число задач на пользователе. Администратор системы видит все проекты, кнопку «Создать проект» и фильтры «Архив» и «Удалённые» с кнопкой «Восстановить». Над списком проектов — блок «Мои задачи»: открытые задачи пользователя по всем проектам (ключ, название, проект, статус, срок, списано/оценка), сортировка по сроку, просроченные сверху.

**7.3. Доска.** Колонки строго по статусам: К выполнению, В работе, На проверке, Готово. Показываются задачи активного спринта; если активного спринта нет, доска пустая с сообщением «Нет активного спринта» и ссылкой на бэклог. Отменённые задачи на доске не показываются. Перетаскивание карточки между колонками выполняет переход статуса по правилам раздела 4; недопустимые колонки подсвечиваются как запрещённые в момент перетаскивания. Если переход требует комментария, открывается модальное окно.

Карточка на доске содержит: ключ, название, иконку типа, иконку приоритета, аватар исполнителя (или пустой круг, если свободна), строку «списано / оценка», срок с красной подсветкой при просрочке (правило в 3.3), индикатор запущенного таймера. На свободной задаче в колонке «К выполнению» кнопка «Взять в работу».

Фильтры доски: исполнитель (множественный выбор + «Без исполнителя» + «Только мои»), тип, приоритет, метка, поиск по ключу и названию. Фильтры сохраняются в URL.

**7.4. Бэклог и спринты.** Страница со списком секций сверху вниз: активный спринт, запланированные спринты, бэклог. В каждой секции строки задач (ключ, название, статус, исполнитель, оценка) и итог секции: число задач и сумма оценок. Задачи перетаскиваются между секциями (только менеджер) и внутри секции (любой участник; ручной порядок сохраняется). Кнопки «Создать спринт», «Запустить», «Завершить» видны только менеджеру. Закрытые спринты доступны через ссылку «Архив спринтов» с отчётом по каждому.

**7.5. Карточка задачи.** Открывается по адресу `/tasks/{key}`, например `/tasks/TM-42`. Состав:

- Заголовок: ключ, название (редактируется по клику), кнопка статуса с выпадающим списком только допустимых переходов, кнопки «Взять в работу», «Старт / Стоп», «Списать время».
- Правая панель: тип, приоритет, исполнитель, автор, спринт, срок, метки, оценка, списано, остаток, прогресс-бар, даты создания, начала и завершения.
- Описание (Markdown-редактор с предпросмотром).
- Вкладки: Вложения (загрузка, предпросмотр картинок, скачивание), Комментарии (с пометкой «из Telegram» для соответствующих), Журнал времени (список записей: кто, дата, длительность, комментарий, источник), История (все изменения полей).

**7.6. Создание задачи.** Модальное окно с полями: проект (предвыбран текущий), название, тип, приоритет, описание, исполнитель, спринт, оценка, срок, метки. Обязательны только проект и название. Поля «Исполнитель» и «Спринт» доступны по правам раздела 2: только менеджеру и администратору системы. Горячая клавиша `C` на любой странице проекта.

**7.7. Уведомления в интерфейсе.** Колокольчик в шапке со списком событий по задачам пользователя: назначение, смена статуса, новый комментарий, возврат на доработку, приближение срока (за 1 день) и просрочка, автоостановка таймера и обрезание записи по дневному лимиту, удаление вашей задачи, добавление в проект и исключение из него. События хранятся 30 дней.

**7.8. Профиль.** Имя, часовой пояс, смена пароля. Блок «Telegram»: кнопка «Привязать Telegram» с кодом и ссылкой (8.1), после привязки — имя аккаунта и кнопка «Отвязать». Блок «Уведомления»: переключатели личных уведомлений из 8.7.

**7.9. Настройки проекта.** Доступны менеджеру и администратору системы. Шесть вкладок:

- Общее: название, описание, часовой пояс проекта; архивация и мягкое удаление проекта (только администратор, правила в 3.2).
- Участники: список участников с ролями; менеджер добавляет существующего пользователя из списка, меняет роль, исключает из проекта. Администратор системы здесь же заводит нового пользователя (email, имя — ему уходит письмо из 7.1) и деактивирует пользователя во всей системе (правила в 3.1).
- Telegram: кнопка «Подключить Telegram-группу» с кодом (8.2), после подключения — название группы и кнопка «Отключить».
- Уведомления: переключатели событий из 8.6 и время ежедневной сводки.
- Журнал (только администратор): аудит действий менеджеров и администраторов по проекту (3.8): кто, когда, что изменил; фильтры по периоду, пользователю и типу действия.
- Корзина (только администратор): удалённые задачи проекта — ключ, название, кто и когда удалил, кнопка «Восстановить». Удалённые задачи и проекты хранятся бессрочно.

## 8. Telegram-бот

Бот работает в двух режимах: личный чат (привязка аккаунта, личные уведомления, свои задачи) и групповой чат проекта (публикация и создание задач, взятие в работу, сообщения о том, кто что взял). Один бот на всю установку; у проекта не более одной группы, а одна группа может обслуживать несколько проектов. Все действия бота проходят через те же правила и права, что и веб-интерфейс; бот не имеет собственной логики задач.

**8.1. Привязка аккаунта пользователя**

1. В веб-интерфейсе в профиле пользователь нажимает «Привязать Telegram». Система генерирует одноразовый код из 8 символов (латиница и цифры), срок действия 10 минут, и показывает кнопку-ссылку `https://t.me/<имя_бота>?start=<код>` и сам код текстом.
2. Пользователь открывает ссылку или пишет боту в личный чат `/start <код>`.
3. Бот проверяет код. Если код верный и не истёк, система записывает `telegram_user_id` и `telegram_username` в профиль, код гасится. Ответ бота: «Аккаунт привязан: Иван Петров (ivan@example.com)».
4. Если код неверный или истёк: «Код не найден или устарел. Сгенерируйте новый в профиле».
5. Если этот Telegram-аккаунт уже привязан к другому пользователю системы: «Этот Telegram уже привязан к другому аккаунту. Сначала отвяжите его командой /unlink».
6. Отвязка: команда `/unlink` в личном чате или кнопка в профиле. После отвязки бот не реагирует на команды этого пользователя, кроме /help и `/start`.

Пользователь без привязки на любую команду (кроме /start и /help) или кнопку получает один и тот же ответ: «Сначала привяжите аккаунт: профиль → Привязать Telegram». В группе этот ответ приходит всплывающим уведомлением (callback alert) или ответом на сообщение пользователя, который бот удаляет через 30 секунд. Команда /help работает и без привязки: показывает список команд и, если аккаунт не привязан, подсказку, как его привязать.

**8.2. Подключение группы к проекту**

1. Менеджер в настройках проекта нажимает «Подключить Telegram-группу». Система выдаёт одноразовый код проекта (8 символов, 15 минут).
2. Менеджер добавляет бота в группу и пишет в ней `/bind <код>`.
3. Бот проверяет: отправитель привязан и является менеджером этого проекта; код действует; у проекта нет другой группы (сама группа может быть уже привязана к другим проектам). При нарушении любого условия бот отвечает причиной и ничего не меняет.
4. При успехе `telegram_chat_id` группы записывается в проект. Ответ бота в группу: «Группа подключена к проекту TM «Тайм-менеджмент». Команды: /help».
5. Отключение: команда `/unbind` в группе (только менеджер этого проекта; если в группе несколько проектов — /unbind <ключ проекта>) или кнопка в настройках проекта. Если бота удалили из группы, привязка снимается автоматически у всех проектов этой группы, их менеджеры получают личное уведомление.
6. Если Telegram превращает группу в супергруппу и присылает `migrate_to_chat_id`, бот переписывает `telegram_chat_id` у всех проектов этой группы на новый; привязка не теряется.

Бот работает с включённым режимом конфиденциальности (privacy mode): в группе он видит только команды, начинающиеся с `/`, ответы на свои сообщения и нажатия кнопок. Обычную переписку группы бот не читает и не хранит. Права администратора группы боту не нужны.

**8.3. Сообщение о задаче в группе**

При создании задачи в проекте с подключённой группой бот публикует в группу сообщение следующего вида (формат HTML Telegram):

```
🆕 Новая задача TM-42 · Задача · Приоритет: Высокий
Настроить экспорт отчёта в CSV

Автор: Анна Смирнова
Спринт: Спринт 7 · Оценка: 3h · Срок: 14.10.2026
Статус: К выполнению · Исполнитель: —

[ Взять в работу ]  [ Открыть ]
```

Правила сообщения:

- Поля Спринт, Оценка, Срок печатаются только если заполнены. Описание задачи в сообщение не включается.
- Кнопка «Открыть» — ссылка на карточку задачи в веб-интерфейсе.
- Кнопка «Взять в работу» показывается только пока задача в статусе `todo` и без исполнителя.
- Бот сохраняет `message_id` этого сообщения в задаче (поле `telegram_message_id`) и при любом изменении статуса, исполнителя, приоритета, оценки, срока или названия редактирует его, а не шлёт новое. Если сообщение старше 48 часов и Telegram не даёт его редактировать, бот публикует новое сообщение и обновляет `telegram_message_id`.
- В сообщении исполнитель указывается по `display_name`, а если у него есть `telegram_username` — дополнительно упоминание `@username`.

**8.4. Взятие задачи в работу из группы**

Два равнозначных способа: кнопка «Взять в работу» под сообщением задачи и команда `/take TM-42` в группе. Последовательность одинаковая:

1. Бот определяет пользователя системы по `telegram_user_id` отправителя. Не привязан — ответ из 8.1, конец.
2. Бот проверяет, что задача принадлежит одному из проектов этой группы и пользователь — участник проекта. Иначе: «Вы не участник проекта TM».
3. Сервер выполняет переход `todo` → `in_progress` по правилам раздела 4 в одной транзакции с блокировкой строки задачи: если два человека нажали кнопку одновременно, задачу получает ровно один, второй получает отказ.
4. Если переход невозможен, бот отвечает всплывающим уведомлением (для кнопки) или ответом на команду (удаляется через 30 секунд): «Задача TM-42 уже в работе, исполнитель: Иван Петров», «Задача TM-42 в статусе Готово, взять нельзя», «Задача TM-42 не найдена».
5. При успехе бот редактирует сообщение задачи (строка «Статус: В работе · Исполнитель: Иван Петров @ivan», кнопка «Взять в работу» убирается) и публикует в группу отдельное сообщение ответом на сообщение задачи:

```
🛠 TM-42 «Настроить экспорт отчёта в CSV» взята в работу — Иван Петров @ivan
```

6. В истории задачи переход записывается с `source = telegram`.

Если задача взята в работу из веб-интерфейса или назначена менеджером, бот публикует в группу то же сообщение; при назначении менеджером текст: «📌 TM-42 «…»: исполнитель Иван Петров @ivan — назначение: Анна Смирнова».

**8.7. Личные уведомления**

Приходят в личный чат привязанному пользователю. Каждое можно отключить в профиле; по умолчанию все включены.

- Вас назначили исполнителем (кто, какая задача, кнопки «Взять в работу» и «Открыть»).
- Вашу задачу вернули на доработку (с комментарием).
- Вашу задачу приняли или отменили.
- Новый комментарий к задаче, где вы исполнитель или автор (кроме ваших собственных).
- Задача, где вы автор, отправлена на проверку (кнопки «Принять» и «Вернуть»; если вы и исполнитель этой задачи, кнопки «Принять» нет; «Вернуть» запрашивает комментарий следующим сообщением).
- Срок вашей задачи завтра (отправляется в 09:00 по часовому поясу пользователя) и срок просрочен (один раз, в день просрочки).
- Таймер остановлен автоматически после 12 часов.
- Запись таймера обрезана по дневному лимиту 24 часа (6.4).
- Ваша задача (вы исполнитель или автор) удалена.
- Вас добавили в проект или исключили из него, изменили вашу роль.

**8.8. Технические требования к боту**

- Получение обновлений через webhook по HTTPS; секрет в заголовке `X-Telegram-Bot-Api-Secret-Token` проверяется на каждом запросе. Long polling допускается только в локальной разработке.
- Каждый `update_id` обрабатывается не более одного раза (храним обработанные id 24 часа). Повторное нажатие кнопки не создаёт повторных действий.
- Ответ на webhook отдаётся сразу (HTTP 200), обработка и отправка сообщений идут через очередь заданий. Нажатие кнопки подтверждается вызовом `answerCallbackQuery` не позже чем через 3 секунды.
- Отправка сообщений с учётом лимитов Telegram: не более 20 сообщений в минуту в одну группу; при ответе 429 повтор через указанный `retry_after`; после 5 неудачных попыток сообщение пишется в лог ошибок и отбрасывается.
- Данные кнопок (`callback_data`) содержат действие и id задачи, например `take:<task_id>`; права проверяются сервером при каждом нажатии, а не при отрисовке кнопки.
- Бот отвечает на русском языке. Тексты сообщений хранятся в одном файле шаблонов, а не разбросаны по коду. Тексты не зависят от рода пользователя: имя ставится после тире, глагол согласуется с задачей («TM-42 принята — Анна Смирнова»).

## 9. REST API

Веб-интерфейс работает через REST API. Telegram-бот работает в том же процессе и вызывает тот же слой сервисов с теми же проверками прав; отдельных «внутренних» путей и обходов для бота нет. Базовый путь `/api/v1`. Формат запросов и ответов JSON, кодировка UTF-8, даты в ISO 8601 (`2026-10-09T14:30:00Z`). Все списки отдают не более `limit` элементов (по умолчанию 50, максимум 200) и `cursor` для следующей страницы; по умолчанию новые сверху.

**9.1. Авторизация.** `POST /auth/login` (email, password) возвращает access-токен JWT (срок 15 минут) и refresh-токен (срок 30 дней, httpOnly cookie). `POST /auth/refresh`, `POST /auth/logout`. Запросы передают `Authorization: Bearer <token>`. Бот определяет пользователя по `telegram_user_id` и выполняет действия от его имени через общий слой сервисов; сервисного токена и HTTP-вызовов API «самому себе» нет. Установка и восстановление пароля (7.1): `POST /auth/password-reset` (email) отправляет ссылку на 24 часа, `POST /auth/password-set` (токен из ссылки, новый пароль) задаёт пароль; токен одноразовый. Refresh-токены хранятся на сервере; при смене пароля, деактивации и команде «Выйти везде» в профиле все токены пользователя отзываются, access-токен доживает не более 15 минут.

**9.3. Ошибки.** Единый формат: `{"error": {"code": "INVALID_TRANSITION", "message": "Переход done → todo не разрешён", "details": {}}}`. Каждый ответ содержит заголовок X-Request-Id; при ошибке он же в details.request\_id и в строке лога. Коды HTTP и коды ошибок: 400 ошибка валидации — VALIDATION_FAILED (`details` содержит список fields с полем и причиной; имя поля — как в JSON запроса, для вложенных — путь вида items[0].title), INVALID_JSON — тело не JSON-объект, пустое или оборвано, INVALID_DURATION (6.1); 401 UNAUTHORIZED — нет токена или истёк; 403 FORBIDDEN — нет прав; 404 NOT_FOUND — не найдено (и проект, в котором пользователь не участник); 405 METHOD_NOT_ALLOWED; 409 конфликт состояния (`INVALID_TRANSITION`, `TASK_ALREADY_TAKEN`, `SPRINT_ALREADY_ACTIVE`, `DAILY_LIMIT_EXCEEDED`, `TIMER_ALREADY_RUNNING`, `VERSION_CONFLICT` — несовпадение `version` при `PATCH` (3.3), `LAST_MANAGER` — деактивация, понижение или исключение единственного менеджера проекта, `PROJECT_ARCHIVED` — изменение в архивном проекте (3.2)), 413 PAYLOAD_TOO_LARGE — вложение больше 50 МБ, 429 RATE_LIMITED — превышен лимит запросов (100 запросов в минуту на пользователя); 500 INTERNAL — внутренняя ошибка, сообщение фиксированное, причина только в логе.

**9.4. События.** Каждое изменение задачи, спринта, комментария, записи времени или состава проекта публикуется во внутреннюю очередь событий: `task.created`, `task.updated`, `task.transitioned`, `task.assigned`, `task.deleted`, `task.restored`, `comment.created`, `attachment.added`, `worklog.created`, `worklog.updated`, `worklog.deleted`, `sprint.started`, `sprint.task_added`, `sprint.task_removed`, `sprint.closed`, `timer.auto_stopped`, `timer.trimmed`, `member.added`, `member.removed`, `member.role_changed`, `user.deactivated`, `project.archived`, `project.deleted`. `task.updated` нужен для редактирования сообщения задачи в группе (8.3), события `member.*` — для уведомлений из 7.7 и 8.7. Событие записывается в таблицу outbox (3.8) в той же транзакции, что и изменение данных; воркер читает outbox по порядку, кладёт задания в очередь asynq и помечает событие отправленным. Так событие не теряется, если Redis недоступен в момент коммита. Отправка сообщений ботом и уведомления в веб-интерфейсе строятся на этих событиях, а не вызываются напрямую из обработчиков API. Внешние вебхуки для сторонних систем в объём работ не входят.

## 10. Нефункциональные требования, стек, приёмка

**10.1. Архитектура**

```
   Браузер (React SPA)            Telegram-клиенты (личные чаты и группы)
          │ REST / JSON                         │ команды, кнопки
          ▼                                     ▼
   ┌──────────────────────┐   webhook   ┌──────────────────┐
   │      API-сервер      │◀────────────│ Telegram Bot API │
   │ Gin, права, сервисы, │             └──────────────────┘
   │ обработчик бота      │                      ▲ sendMessage, editMessageText
   └──────────┬───────────┘                      │
              │ SQL (данные + outbox в одной транзакции)
              ▼                                  │
   ┌──────────────────┐   outbox → очередь  ┌────┴────────────────────────┐
   │    PostgreSQL    │────────────────────▶│ Воркер (asynq на Redis)     │
```

**10.4. Критерии приёмки.** Работа сдаётся в два этапа. Этап принимается, когда на стенде проходят его сценарии ниже; сценарии с Telegram относятся ко второму этапу.

- [ ] Первый администратор создаётся CLI-командой и входит по ссылке; он создаёт проект `TM`, добавляет менеджера и двух исполнителей; каждый входит по ссылке из письма.

- [ ] Исполнитель привязывает Telegram по коду; менеджер подключает группу командой `/bind`.
- [ ] При создании задачи в веб-интерфейсе в группе появляется сообщение с кнопкой «Взять в работу» не позже 5 с.
- [ ] Два исполнителя одновременно нажимают «Взять в работу»: задачу получает один, второй видит «Задача … уже в работе, исполнитель: …», в группе ровно одно сообщение «… взята в работу — …», на доске задача в колонке «В работе» с правильным исполнителем.
- [ ] `/take TM-5` в группе даёт тот же результат, что кнопка. Непривязанный пользователь получает подсказку о привязке, задача не меняется.
- [ ] Исполнитель списывает `1h 30m` через `/log` и `45m` через веб; в карточке сумма `2h 15m`, в отчёте по пользователям за сегодня `2.25`.
- [ ] Таймер: старт на одной задаче, старт на другой — первый остановлен и создана запись с `source = timer`.
- [ ] Переход `done` → `todo` через API отклоняется с `409 INVALID_TRANSITION`; исполнитель не может принять свою задачу, даже если он её автор (`403`).

- [ ] Группа подключена к двум проектам: `/take 5` без ключа получает подсказку со списком проектов, `/take TM-5` работает, `/tasks` показывает задачи обоих проектов с разбивкой по проектам.
- [ ] `/new TM Настроить экспорт` в группе создаёт задачу в бэклоге с автором-отправителем; в группе появляется карточка из 8.3.
- [ ] Вложение 49 МБ загружается в карточке задачи и скачивается, файл 51 МБ отклоняется; исполнитель не может удалить чужое вложение (`403`).
- [ ] Два пользователя открывают одну карточку и меняют название: второй получает `409 VERSION_CONFLICT` и видит чужую правку; первая правка не потеряна.
- [ ] Менеджер удаляет задачу с записями времени: она исчезает с доски, сумма в отчёте по пользователям не меняется; администратор восстанавливает её.

- [ ] Восстановление пароля: ссылка из письма работает один раз, повторное открытие отклоняется, пароль короче 10 символов не принимается.
- [ ] Архивация проекта: доска только для чтения, `PATCH` задачи отвечает `409 PROJECT_ARCHIVED`, `/take` в группе получает ответ об архиве; отчёт по времени по проекту открывается.
- [ ] Ежедневная сводка: менеджер включает сводку и ставит время через 2 минуты; в группу приходит сводка по активному спринту со списком просроченных задач.
- [ ] Напоминание о сроке: у задачи срок завтра — в 09:00 по поясу исполнителя приходит личное сообщение; на следующий день — «срок просрочен» ровно один раз (время стенда сдвигается).
- [ ] Автостоп таймера: таймер, запущенный более 12 часов назад, остановлен воркером на отметке 12h, запись создана, пользователь получил уведомление в Telegram и в колокольчике.

Сценарии входа по ссылке, создания и запуска спринта, перетаскивания на доске, списания времени, таймера и завершения спринта автоматизированы в Playwright и запускаются в CI.
- [ ] Нагрузка: на стенде со сгенерированными 100 000 задач и 1 000 000 записей времени при 50 одновременных пользователях 95% запросов к доске, карточке и списку задач быстрее 300 мс, отчёт по времени за месяц быстрее 3 с (измеряется k6 или аналогом, скрипт генерации данных входит в поставку).

## 12. Интеграция с GitHub

TaskFlow связывает задачи с ветками и pull request'ами GitHub по ключу задачи и сам двигает статус по PR. Решения заказчика от 12.10.2026: подключение — GitHub App, связь — ключ задачи в имени ветки или заголовке PR, статусы — PR → «На проверке», merge → «Готово». Публикация задач в GitHub Issues и обратная синхронизация пока не делаются.

**12.1. Подключение.** Администратор создаёт GitHub App и указывает в `.env` его id, приватный ключ и секрет вебхуков; ключи хранятся только там. App ставится на репозиторий (или организацию) с правами: Pull requests — чтение, Contents — чтение, Metadata — чтение; события вебхука — `pull_request`, `create` и `delete` (создание и удаление ветки). Менеджер проекта во вкладке «GitHub» настроек проекта (7.9) выбирает репозиторий из доступных App и может отвязать его.

**12.2. Вебхуки.** Приём на `POST /api/v1/github/webhook`. Подпись `X-Hub-Signature-256` проверяется секретом App, неверная — `401` без обработки. Доставка с уже виденным `X-GitHub-Delivery` не обрабатывается повторно (идемпотентность). Обработка — через outbox и воркер, как остальные события (9.4); ответ GitHub — сразу `202`.

**12.3. Связь задачи с веткой и PR.** Ключ задачи ищется в имени ветки и в заголовке PR без учёта регистра (`feat/tm-42-login`, `TM-42: вход`). Учитываются только ключи проекта, к которому привязан репозиторий; несколько ключей — PR связывается со всеми. В карточке задачи (7.5) — блок «GitHub»: ветки и PR со ссылками и состоянием (открыт, черновик, влит, закрыт). Удалённая задача и архивный проект связи не получают.

**12.4. Статус задачи по PR.** Статус меняется только разрешёнными переходами раздела 4; если до цели несколько шагов, выполняется цепочка, и каждый шаг пишется в историю (3.7) с `source = github`, ссылкой на PR и автором PR (12.5). Задача в `done` или `cancelled` по PR не меняется.

| Событие PR | Условие | Итог |
| --- | --- | --- |
| Открыт, переоткрыт или выведен из черновика | задача в `todo` | исполнитель не задан — назначается автор PR; `todo → in_progress → review` |
| То же | задача в `in_progress` | `in_progress → review` |
| Влит (merged) | задача в `in_progress` или `review`, других открытых PR задачи нет | `in_progress → review → done` или `review → done` |
| Закрыт без слияния | задача в `review`, других открытых PR задачи нет | `review → in_progress` с комментарием-причиной «PR #N закрыт без слияния» |
| Черновик, смена заголовка | — | статус не меняется; новый ключ в заголовке связывает PR с задачей |

Автор PR назначается только если его GitHub-аккаунт связан (12.5) и он активный участник проекта; иначе задача без исполнителя статус не меняет, PR только связывается. Автор шага в истории — связанный пользователь или система (`user_id` пуст) с логином GitHub в примечании.

**12.5. Связка аккаунтов.** В профиле (7.8) пользователь привязывает свой GitHub-логин через вход в GitHub (авторизация пользователя того же GitHub App); один GitHub-логин — один пользователь. Автор PR со связанным аккаунтом указывается в истории задачи; без связки — «GitHub (логин)».

**12.6. События и права.** Новые события 9.4: `github.linked` (у задачи появилась ветка или PR) и `github.pr_changed` (сменилось состояние PR); смена статуса публикует обычный `task.transitioned`. Служебное событие `github.delivery` переносит принятую доставку вебхука из outbox в воркер (12.2). Права (раздел 2): привязать и отвязать репозиторий — менеджер проекта и администратор; привязать свой GitHub-аккаунт — любой пользователь.

**12.7. Уточнения заказчика от 12 октября 2026.** К проекту привязывается один репозиторий, и репозиторий — к одному проекту. Черновик PR статус не меняет — только показывается в карточке; «На проверке» ставит обычный PR. Отдельных сообщений о PR в Telegram нет: группа получает обычное сообщение о смене статуса (8.6).

**12.8. Данные и API.** Раздел дополняет 3, 2, 7.9 (седьмая вкладка «GitHub»), 9.2 и 9.4.

| Что | Поля и правила |
| --- | --- |
| Проект (3.2) | `github_repo` (`owner/name`, уникален), `github_installation_id`; пусто — репозиторий не привязан |
| Пользователь (3.1) | `github_login` (уникален, пусто — не связан) |
| Связь с GitHub | `task_id`, `kind` (`branch`, `pr`), `number` (для PR), `name` (ветка или заголовок PR), `url`, `state` (`open`, `draft`, `merged`, `closed`), `author_login`; пара задача + ссылка уникальна |
| Доставки вебхуков | `delivery_id` (ключ), время приёма; хранятся 7 дней |
| История (3.7) | `source` допускает ещё `github` |
| API (9.2) | `POST /github/webhook` (без JWT, по подписи); `GET/PUT/DELETE /projects/{key}/github` (менеджер); `GET /github/repositories` — репозитории, доступные App (менеджер); `GET /me/github/connect`, `DELETE /me/github` — связка аккаунта, `GET /github/callback` — возврат из GitHub после входа (без JWT, по подписанному `state`); связи задачи — `GET /tasks/{key}/github`, как история и комментарии; не поле `github` в карточке `GET /tasks/{key}` |
