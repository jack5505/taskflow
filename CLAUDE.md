# TaskFlow — правила для работы с кодом

Система управления задачами и временем с Telegram-ботом. Единственный источник требований — `docs/TZ.md`. Если код и ТЗ расходятся, прав ТЗ; если ТЗ молчит — не додумывать, а спросить и после ответа дописать в ТЗ.

## Карта проекта

| Каталог | Что это | Подробнее |
|---|---|---|
| `api/` | Go 1.25, Gin. Один бинарник `taskflow` с режимами `api`, `worker`, `admin` | `api/CLAUDE.md` |
| `web/` | React 18 + TypeScript (Vite). Сборка встраивается в бинарник api | `web/CLAUDE.md` |
| `docs/TZ.md` | Техническое задание, 11 разделов. Ссылайся на пункты вида §4, §8.5 | — |
| `docker-compose.yml` | Стенд: api (127.0.0.1:8100), worker, postgres 16, redis 7 | — |
| `Makefile` | Все команды сборки и тестов; Go запускается только в контейнере | `make help` |

## Как вести работу

Полный процесс — в `CONTRIBUTING.md`. Главное:

- В `main` напрямую не пишем: ветка → pull request → код-ревью → зелёный CI → squash-merge. Ветка `main` защищена, прямой push отклоняется.
- Каждая задача — issue на GitHub (`jack5505/taskflow`) с пунктами ТЗ и критериями готовности. Эпики помечены `epic`, этапы — milestones «Этап 1» и «Этап 2». Перед началом прочитай issue и указанные пункты ТЗ целиком.
- Ветка на задачу: `feat/<номер>-<кратко>`, например `feat/8-postgres-migrations`. PR в `main` по шаблону `.github/pull_request_template.md`, в описании — `Closes #<номер>` и как проверить.
- Мерж только после код-ревью, одного ревью достаточно: ревью делает Claude Code (`/code-review`), результат — комментарием в PR. Замечания исправляются новыми коммитами, без force-push; после закрытия замечаний PR сливается.
- Критерии готовности из issue — чек-лист PR. Не закрывать issue, пока все пункты не выполнены и CI не зелёный.
- Коммиты на русском, в повелительном наклонении: «Добавить миграцию users». Без строк Co-Authored-By и упоминаний инструментов, которыми писался код.
- Не менять ТЗ в репозитории напрямую: исходник живёт в Claude Docs, `docs/TZ.md` — выгрузка. Расхождение нашёл — скажи, правка идёт сначала в Docs.

## Окружение сервера

- На сервере нет локального Go: `make build`, `make test`, `make lint` работают через `docker run golang:1.25-alpine`. Не ставить Go в систему и не писать инструкции «установите Go». На этом сервере нет и `make` — бери команду `docker run …` из соответствующей цели Makefile и запускай её напрямую.
- Интеграционные тесты поднимают PostgreSQL через testcontainers внутри контейнера golang: нужны `-v /var/run/docker.sock:/var/run/docker.sock`, `--add-host=host.docker.internal:host-gateway` и `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` — см. `GO_TEST` в Makefile.
- Порты 80, 443, 3001, 3080, 5005, 8080, 8081, 8090, 8443 заняты другими сервисами (mahalla, quizlet). TaskFlow слушает только `127.0.0.1:8100`; наружу — через nginx сервера, конфиг в `~/mahalla-dev/nginx/extra/` (issue #6). Чужие контейнеры и nginx не перезапускать.
- Секреты только в `.env` (в git не попадает). Образец — `.env.example`; новая переменная добавляется туда же с комментарием и в `api/internal/config`.

## Архитектурные решения, которые не обсуждаются заново

- Бот не ходит в API по HTTP: обработчики бота вызывают тот же слой сервисов, что и HTTP-обработчики (§9.1). Проверки прав — одни на всех.
- Каждое изменение данных пишет событие в таблицу outbox в той же транзакции; воркер переносит события в asynq (§9.4). Отправлять сообщения или письма прямо из HTTP-обработчика нельзя.
- Схема базы — только миграции golang-migrate в `api/migrations`. `AutoMigrate` запрещён.
- Формат ошибок API один (§9.3): `{"error":{"code","message","details"}}`, в каждом ответе `X-Request-Id`.
- Мягкое удаление задач и проектов, оптимистическая блокировка задач через `version` / `If-Match`, блокировка строки при взятии задачи — см. §3.3, §4.
- Тексты бота и писем — в одном файле шаблонов, без зависимости от рода пользователя (§8.8).

## Тесты и качество

- Серверные тесты — на настоящих PostgreSQL и Redis через testcontainers; моки базы не использовать. Порог покрытия 80% проверяет CI.
- Все переходы статусов из §4 и сценарий одновременного взятия задачи должны быть покрыты тестами — это критерий приёмки.
- Перед PR: `make fmt lint test` и `cd web && npm run lint && npm run build`.
